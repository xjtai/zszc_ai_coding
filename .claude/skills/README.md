# 技术中台知识库（以 skills 承载）

绿地项目（多智能体客服）里没有存量系统，`knowledge_refs` 一直留空。做**存量系统更新**时不行了——Agent 不知道你们系统里"订单"指哪张表、"删除"是删数据还是隐藏，只能靠常识猜，而常识在每个公司都不一样。这个目录就是把这些"只有你们内部才知道的事"喂给 Agent。

## 为什么用 skills 承载，而不是塞进 CLAUDE.md

CLAUDE.md 里的东西**每次对话都占上下文**。知识库有几十上百条，全塞进去会挤掉真正干活的空间。

skill 是**按需加载**的：`description` 常驻（很短，用来判断要不要翻），正文只在命中时才读进来。所以：

> **`description` 写得好不好，决定这条知识会不会被用上。** 正文写得再准，description 没让 Agent 意识到"这事该查你"，它就永远不会被打开。

写 description 的要点：**写触发场景，不要写内容摘要**。

- ❌ `订单域的相关知识和规范`——Agent 无法判断什么时候该翻
- ✅ `涉及订单、退货、退款、删除订单时必读。回答"删除订单是删数据还是隐藏"……`

## 四层分层与 SDD 的对应

| 层 | 放什么 | 谁读它 |
|---|---|---|
| 业务层 | 词条边界、操作场景、业务原则 | `spec.md` 消歧 |
| 架构层 | 服务图谱、系统间依赖、约束条件 | `spec.md` 影响面、`plan.md` 选型 |
| 系统层 | API 定义、策略规范、数据模型 | `plan.md` 数据模型、`tasks.md` |
| 基建层 | 分片策略、命名规范、阈值 | `tasks.md`、`eval.md` |

命名用 `kb-<层>-<主题>`，如 `kb-order-domain`（业务层）、`kb-payment-api`（系统层）。

## 怎么用

1. **写之前**：复制 `_template/SKILL.md` 到 `kb-<你的主题>/SKILL.md`，照着填。参考已填好的 `kb-order-domain/`。
2. **一条只讲一件事**：一个 skill 塞五个主题，description 就没法写准，命中率反而下降。宁可拆多个。
3. **在 SDD 文档里登记**：spec/plan/tasks 的 frontmatter 有 `knowledge_refs` 字段，正文引用了哪条就登记进去，例如：

   ```yaml
   knowledge_refs: [kb-order-domain]
   ```

4. **learnings.md 要回流**：这一轮踩的坑，如果根因是"知识库里没写"或"写得不清楚"，就在 `learnings.md` 的"回流"里指明——**该新增哪个 skill，或改哪条的哪一句**。这是知识库能越用越准的唯一途径；只记在复盘里不回流，下一轮同一个坑还会踩。

## 最小可用标准

一条 skill 合格只要满足三点，不必追求完备：

- [ ] `description` 说清了**什么时候该翻它**（不是内容摘要）
- [ ] 「结论」一句话说死，没有"视情况而定"
- [ ] 「不是」那一栏填了——**词义漂移都是从边界模糊开始的，这栏最值钱**
