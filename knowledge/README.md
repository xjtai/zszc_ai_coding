# 企业本体知识库

多智能体客服那轮是**从零新建**（业内也叫"绿地项目"，greenfield——一块空地，想怎么盖怎么盖），约束全都来自需求本身，所以 `knowledge_refs` 一直留空。

**改存量系统**（对应"棕地项目"，brownfield——地上已经盖过东西，动工前得先搞清楚地下埋着什么）就不行了：这时候一大半约束不来自需求，而来自"系统现在是怎么长的"——而这部分恰恰**不写在需求文档里**，只存在于老员工脑子里。Agent 不知道你们系统里"订单"指哪张表、"删除"是删数据还是隐藏，只能靠常识猜，而常识在每个公司都不一样。

这个目录就是把这些"只有你们内部才知道的事"喂给 Agent。

**格式是工具中立的**：普通 Markdown + YAML frontmatter，Claude Code、Cursor、通义灵码、Copilot 都能用，只是加载方式不同（见下方"各工具怎么接"）。

## 一条知识 = 一个文件

```
knowledge/
  _template.md              最小模板，复制它开始写
  kb-order-domain.md        样例·业务层——「订单」「删除」「退货退款」的词条边界
  kb-order-downstream.md    样例·架构层——改订单主表要通知哪三个下游
  kb-refund-api.md          样例·系统层——退款接口的实际约束（与文档有出入）
  kb-naming-legacy.md       样例·基建层——订单域命名例外，不要统一
  kb-<你的主题>.md
```

四条样例覆盖四层，**都取自同一个订单域**——真实知识库就是这样长的：同一块业务，从词义、依赖、接口到命名各有各的坑。写自己的条目前先挑一条同层的看看。

命名 `kb-<主题>.md`。**一个文件只讲一件事**——塞五个主题进去，`description` 就没法写准，反而更难被用上。宁可拆多个。

## description 是最关键的一行

知识库有几十上百条，不可能全塞进上下文（那会挤掉真正干活的空间）。实际用法都是**按需加载**：先看 `description` 判断这条要不要翻开，命中了才读正文。所以：

> **`description` 写得好不好，决定这条知识会不会被用上。** 正文写得再准，description 没让 Agent 意识到"这事该查你"，它就永远不会被打开。

要点：**写触发场景，不要写内容摘要**。

- ❌ `订单域的相关知识和规范`——Agent 无法判断什么时候该翻
- ✅ `涉及订单、退货、退款、删除订单时必读。回答"删除订单是删数据还是隐藏"……`

## 为什么叫"本体"

本体（ontology）来自知识工程，指**一个组织内部对概念、边界和关系的共同约定**——"我们说『订单』时指的是什么、它和『配送单』什么关系、『删除』在我们这儿意味着什么"。

这正是 Agent 最缺的东西。它读得懂代码、查得到表结构，但**没法从代码里反推出"这个词在你们公司的约定俗成"**——那是一层只在人脑和口头交流里传承的语义。所以这个库不是"技术文档的副本"，而是把这层约定**显式写下来**。

判断一条该不该收进来，一句话：**新人入职三个月才慢慢搞明白的那些事**。写在设计文档里的不用抄进来，Agent 自己会读。

## 四层与 SDD 的对应

每层放的都是**约定与陷阱**，不是文档副本——照着上面那条判据来：

| 层 | 放什么 | 谁读它 | 样例 |
|---|---|---|---|
| 业务层 | 词条边界：这个词在我们这儿的特殊含义 | `spec.md` 消歧 | `kb-order-domain.md` |
| 架构层 | 改这里会牵动谁；文档上没画的依赖 | `spec.md` 影响面、`plan.md` 选型 | `kb-order-downstream.md` |
| 系统层 | 接口/数据模型的**实际**约束——文档没写或写错的那些 | `plan.md` 数据模型、`tasks.md` | `kb-refund-api.md` |
| 基建层 | 历史包袱、例外规则、真实阈值 | `tasks.md`、`eval.md` | `kb-naming-legacy.md` |

同一层里，什么该收什么不该收，差别很大：

| 层 | ❌ 别抄（文档里有，Agent 自己会读） | ✅ 该收（只在人脑里） |
|---|---|---|
| 架构层 | 服务清单、部署拓扑图 | "改订单主表要通知财务、风控、客服工单，漏一个就对账不平" |
| 系统层 | 退款接口的字段列表 | "文档说支持批量，实际超过 50 笔必超时，而且非幂等" |
| 基建层 | 命名规范文档 | "订单域历史原因全是下划线，别去统一，动了 20 个下游都要改" |

## 各工具怎么接

| 工具 | 接法 |
|---|---|
| 通用（任何工具） | 对话里直接引用：「参考 `knowledge/kb-order-domain.md`，做需求理解」 |
| Cursor / 通义灵码 / Copilot | 用 `@` 引用文件；或把 `knowledge/` 加进项目规则/上下文目录 |
| Claude Code | 想要**自动按需加载**，把条目转成 skill：`.claude/skills/<name>/SKILL.md`（frontmatter 已经是兼容格式，复制过去即可）。不转也能用，同"通用"那行。 |

不确定用哪种就用"通用"那行——显式引用最不容易出错，只是每次要自己点名文件。

## 怎么用

1. **写之前**：复制 `_template.md` 成 `kb-<你的主题>.md`，照着填，并挑一条**同层**的样例对照（四层各有一条，见上方目录）。
2. **在 SDD 文档里登记**：spec/plan/tasks 的 frontmatter 有 `knowledge_refs` 字段，正文引用了哪条就登记进去：

   ```yaml
   knowledge_refs: [kb-order-domain]
   ```

3. **learnings.md 要回流**：这一轮踩的坑，如果根因是"知识库里没写"或"写得不清楚"，就在 `learnings.md` 的"回流"里指明——**该新增哪个文件，或改哪条的哪一句**。这是知识库能越用越准的唯一途径；只记在复盘里不回流，下一轮同一个坑还会踩。

## 最小可用标准

一条知识合格只要满足三点，不必追求完备：

- [ ] `description` 说清了**什么时候该翻它**（不是内容摘要）
- [ ] 「结论」一句话说死，没有"视情况而定"
- [ ] 「不是」那一栏填了——**词义漂移都是从边界模糊开始的，这栏最值钱**
