# 订单主表的下游依赖：改之前要通知谁

## 结论

`trade_order` 主表有 **3 个实时直连下游**，任何字段增删、状态机改动、软删除逻辑变更，**都要提前一个迭代通知这三方**：财务对账、风控模型、客服工单。

## 边界

- **是**（实时直连，改了立刻出问题）：
  - **财务对账**——每日凌晨全量拉取，缺单直接对账不平，会出结算差错
  - **风控模型**——实时消费订单状态变更，字段缺失会让模型静默降级（不报错，但拦截率掉）
  - **客服工单**——按订单号反查，查不到订单工单就建不了
- **不是**（不用通知）：
  - **推荐系统**——走数仓 T+1 同步，schema 变更由数仓适配层兜住，不受实时影响
  - **BI 报表**——同上，走数仓

## 最容易搞错的

PRD 里只写「用户可以删除订单」，Agent 把它当成订单服务的**局部改动**，只改了订单服务自己的查询逻辑就交付了。结果上线当晚：财务对账缺了当天所有被删订单，客服收到用户投诉却查不到工单。

**根因不是代码写错了，是影响面没评估**——`trade_order` 是被三方直连消费的，不是订单服务的私有表。凡是动它，`spec.md` 的影响面必须列全这三方，`plan.md` 的方案要写清各自怎么兼容。

**风控那条最隐蔽**：它不会报错，只会悄悄降低拦截率，可能上线两周后才从业务指标上看出来。
