# 退款接口的实际约束（与接口文档有出入）

## 结论

- **单次最多 50 笔**。文档写的"支持批量"没写上限，实际超过 50 笔必然网关超时（30s）。
- **非幂等**。必须自带 `request_id` 去重，否则重试 = 重复退款，真金白银出去。
- **异步返回**。接口返回 200 只代表"受理成功"，不代表退款到账；到账状态要另外查或等回调。

## 边界

- **是**：支持部分退款（`amount` 可小于订单金额），支持同一订单多次部分退款直到退完
- **不是**：不支持跨订单合并退款——每个 `order_id` 必须单独一条，别为了省调用次数把多个订单塞进一次请求
- **不是**：不支持撤销。退款一旦受理无法撤回，只能走人工资金追回流程

## 最容易搞错的

Agent 读了接口文档看到"支持批量退款"，生成了一次传 200 笔的实现。功能测试用 3 笔数据全过，压测直接超时，且**超时后有一半已经退成功了**——因为网关超时不等于服务端没处理。

第二个坑更贵：Agent 给退款调用加了"失败自动重试 3 次"的通用兜底。因为接口非幂等，一次网络抖动导致同一笔退款执行了 3 遍。**任何退款重试都必须带 `request_id`**，这条要写进 `plan.md` §6 不改清单。

第三个：把"接口返回 200"当成"退款成功"回复给用户，用户查账户没到账就来投诉。正确话术是"退款申请已提交，3-5 个工作日到账"——`prd.md` §7 Golden Path 里的措辞就是这么定的，不是随便写的。
